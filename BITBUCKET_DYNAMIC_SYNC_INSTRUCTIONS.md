# BITBUCKET_DYNAMIC_SYNC_INSTRUCTIONS.md

## Goal

Update the existing Team Pulse / Velocity Analytics application with a dynamic Bitbucket sync flow.

The user must NOT manually maintain Bitbucket project keys or repository slugs for each team.

The application already has:
- application projects / teams in the database
- team members / SSOs in the database
- Spring Boot backend
- React frontend
- JdbcTemplate
- H2 for now
- MySQL planned later

The new Bitbucket sync flow must dynamically discover Bitbucket projects and repositories, resolve selected team SSOs to Bitbucket users, find PRs authored by those users across all accessible repositories, enrich the PRs, and save them without duplicates.

Do not recreate the application.
Do not introduce JPA.
Use `JdbcTemplate`.

# 4. SSO to Bitbucket User Mapping

Create table:

```sql
CREATE TABLE IF NOT EXISTS sso_userid (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id BIGINT NOT NULL,
    sso VARCHAR(255) NOT NULL,
    bitbucket_user_id VARCHAR(100),
    bitbucket_username VARCHAR(255),
    bitbucket_slug VARCHAR(255),
    last_resolved_at TIMESTAMP WITH TIME ZONE,

    CONSTRAINT uk_sso_userid UNIQUE (project_id, sso)
);
```

Use `UNIQUE(project_id, sso)` to prevent duplicate mappings.

---

# 5. Resolve SSO Dynamically

For each selected SSO:

1. check `sso_userid`
2. if a valid mapping exists, reuse it
3. if missing, call Bitbucket Data Center user lookup
4. resolve:
   - internal numeric user ID
   - username
   - slug if available
5. insert or update `sso_userid`

Do not resolve known users on every sync unless mapping is missing, stale, or a full refresh is requested.

For PR author filtering, prefer the Bitbucket username / slug supported by the PR endpoint.

---

# 6. Dynamic Bitbucket Project Catalog

Do NOT manually store team-to-Bitbucket-project mappings.

Discover Bitbucket projects dynamically.

Call:

`GET /rest/api/1.0/projects?limit=100&start={start}`

Follow pagination using:
- `isLastPage`
- `nextPageStart`

---

# 7. Dynamic Repository Catalog

For every discovered Bitbucket project call:

`GET /rest/api/1.0/projects/{projectKey}/repos?limit=100&start={start}`

Follow pagination.

Collect:
- project key
- repository slug
- repository name

Do not hardcode repository slugs.

---

# 8. Cache the Catalog

Create:

```sql
CREATE TABLE IF NOT EXISTS bitbucket_project (
    project_key VARCHAR(255) PRIMARY KEY,
    project_name VARCHAR(500),
    active BOOLEAN DEFAULT TRUE,
    last_discovered_at TIMESTAMP WITH TIME ZONE
);
```

Create:

```sql
CREATE TABLE IF NOT EXISTS bitbucket_repository (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_key VARCHAR(255) NOT NULL,
    repo_slug VARCHAR(500) NOT NULL,
    repo_name VARCHAR(500),
    active BOOLEAN DEFAULT TRUE,
    last_discovered_at TIMESTAMP WITH TIME ZONE,

    CONSTRAINT uk_bitbucket_repo UNIQUE(project_key, repo_slug)
);
```

This catalog is a cache of Bitbucket structure. It is NOT a team-to-repository mapping.

# 10. Automatic Catalog Behavior

For normal Bitbucket sync:
- if catalog is empty, refresh automatically
- if catalog is older than configured TTL, refresh automatically
- otherwise reuse cached catalog

Suggested config:

```yaml

  catalog:
    ttl-hours: 24
```

# 12. Sync Flow

`BitbucketSyncService` must:

1. validate application project
2. validate selected SSOs belong to that project
3. resolve selected SSOs to Bitbucket users
4. ensure repository catalog exists and is fresh
5. load cached Bitbucket repositories
6. search PRs authored by selected users in every accessible repository
7. deduplicate discovered PRs
8. enrich only matching PRs
9. normalize PR data
10. upsert PR data
11. return sync summary

---

# 13. PR Discovery Across All Repositories

Do not use browser-only plugin servlet endpoints.

For each repository use the official Bitbucket Data Center PR endpoint:

`GET /rest/api/1.0/projects/{projectKey}/repos/{repoSlug}/pull-requests`

Use:
- `state=ALL`
- `limit=100`
- participant / author filters supported by the current Bitbucket version
- `start` pagination

Filter for author role.

Use selected Bitbucket usernames.

If the API limits participant filters per request, partition selected users into supported batches.

Do not scan separately for each user if multiple authors can be passed in one request.

---

# 14. Date Filtering

User supplies:
- `fromDate`
- `toDate`

Retain PRs relevant to the requested date range.

At minimum retain PRs whose `PR Created At` falls in range.

For merged analytics, also retain PRs whose merge date is in range if required by existing reporting logic.

Keep date filtering in the backend.

# 18. Timestamp Rules

`PR Created At = pullRequest.createdDate`

`First Commit At = MIN(commit.committerTimestamp)`

`PR Merged At = activity.createdDate where action == MERGED`

Fallback for merged time:
`pullRequest.closedDate` only when state is `MERGED`.

`First Review Engagement At` = earliest relevant reviewer activity.

Missing timestamps must be `null`, not zero.

---

# 19. Jira Key Extraction

Use this priority:

1. `commit.properties["jira-key"]`
2. PR title
3. PR description
4. source branch
5. commit message

Fallback regex:

```regex
([A-Z][A-Z0-9]+-\d+)
```

Store mapping source as:

```text
COMMIT_PROPERTY
PR_TITLE
PR_DESCRIPTION
SOURCE_BRANCH
COMMIT_MESSAGE
NONE
```

# 20. bitbucket_pr Table

Create:

```sql
CREATE TABLE IF NOT EXISTS bitbucket_pr (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    application_project_id BIGINT,
    project_key VARCHAR(255) NOT NULL,
    project_name VARCHAR(500),
    repo_slug VARCHAR(500) NOT NULL,
    repository_name VARCHAR(500),
    pr_id BIGINT NOT NULL,
    author_name VARCHAR(500),
    author_username VARCHAR(255),
    author_user_id VARCHAR(100),
    title VARCHAR(2000),
    description CLOB,
    source_branch VARCHAR(1000),
    destination_branch VARCHAR(1000),
    state VARCHAR(100),
    jira_key VARCHAR(100),
    jira_mapping_source VARCHAR(100),
    pr_created_at TIMESTAMP WITH TIME ZONE,
    first_commit_at TIMESTAMP WITH TIME ZONE,
    first_review_engagement_at TIMESTAMP WITH TIME ZONE,
    pr_merged_at TIMESTAMP WITH TIME ZONE,
    cycle_start TIMESTAMP WITH TIME ZONE,
    cycle_start_source VARCHAR(100),
    cycle_time_days DOUBLE,
    last_synced_at TIMESTAMP WITH TIME ZONE,

    CONSTRAINT uk_bitbucket_pr UNIQUE(project_key, repo_slug, pr_id)
);
```

Never insert blindly.

Existing PR -> UPDATE.
New PR -> INSERT.

Use `JdbcTemplate.batchUpdate()`.

Recommended batch size: `500`.

# 21. Enrichment Optimization

Before calling commits and activities, check the existing database record.

If a PR is already `MERGED` and has:
- `prCreatedAt`
- `firstCommitAt`
- `prMergedAt`

then normally skip detailed enrichment.

Refresh only when:
- `fullRefresh=true`
- required data is missing
- existing logic says source data changed

OPEN PRs must remain refreshable.

# 22. Optional User-to-Repository Activity Cache

Optional optimization table:

```sql
CREATE TABLE IF NOT EXISTS bitbucket_user_repo_activity (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    bitbucket_username VARCHAR(255) NOT NULL,
    project_key VARCHAR(255) NOT NULL,
    repo_slug VARCHAR(500) NOT NULL,
    last_pr_seen_at TIMESTAMP WITH TIME ZONE,
    last_scanned_at TIMESTAMP WITH TIME ZONE,

    CONSTRAINT uk_user_repo_activity
        UNIQUE(bitbucket_username, project_key, repo_slug)
);
```

Whenever a PR is found for a user in a repository, upsert this table.

Future syncs may prioritize known repositories, but must periodically perform a full scan so new contribution repos are discovered.

---

# 23. Controlled Concurrency

Do not create one thread per repository.

Use controlled concurrency.

Suggested config:

```yaml
bitbucket:
  sync:
    concurrency: 5
    full-scan-days: 7
```

---

# 24. Failure Isolation

If one repository fails:
- record the error
- continue other repositories

If one SSO cannot be resolved:
- record the SSO error
- continue other users

If one PR enrichment call fails:
- record the PR error
- continue other PRs

Do not fail the entire sync because of one item unless the Bitbucket service itself is unavailable.

# 32. Important Architecture Rule

The application project is used to determine team members.

It must NOT be treated as a Bitbucket project mapping.

Correct:

```text
Application Team
      ↓
Team SSOs
      ↓
Bitbucket Users
      ↓
ALL accessible Bitbucket projects/repos
      ↓
PRs authored by selected users
```

Incorrect:

```text
Application Team
      ↓
one manually configured Bitbucket project/repo
```
